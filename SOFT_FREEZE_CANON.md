## Known Missing Closure — Reconnect Trust Gap

The current evidence proves that moved guidance still exists and that reconnect routes are emitted.

It does not prove the stronger runtime claim:

> An agent will always recognize that a moved rule is needed, retrieve the correct guidance before acting, and avoid unnecessary retrieval when the rule is irrelevant.

Byte-for-byte preservation is therefore not equivalent to semantic reconnect compliance.

A candidate hidden-task benchmark has been identified but is intentionally deferred. A future benchmark could measure:

- missed retrievals — a moved rule was required but not read;
- unnecessary retrievals — a guide was read when it was not needed;
- pre-action compliance — the guide was retrieved before consequential action;
- semantic routing — the agent reconnects even when the task does not repeat route keywords;
- added latency / overhead from the reconnect path.

This is a valid open question, not a current release blocker.

## Why the Reconnect Benchmark Is Deferred

The benchmark would be useful if reconnect trust becomes a repeated adoption barrier or an observed failure mode.

It is not currently justified merely because one or a few experienced users can imagine the failure mode. Experienced users may already understand or manually implement conditional routing, while less experienced users may not yet perceive instruction-surface growth as a problem.

Running a large benchmark now could spend substantial effort pulling future expectations into the present without evidence that the result would materially change adoption.

The question is preserved so it can be reopened when the evidence changes.

## Separate Future Candidate — Orchestration Boundary Layer

Multi-agent authority boundaries are not the same problem as instruction-volume control.

AGENTS.md Compactor addresses how much instruction material remains always active and how conditional material remains reconnectable.

A future orchestration system may need a separate coordinator-owned representation of who may do what, where authority transfers, and how boundaries between multiple agents are validated.

Do not merge that problem into Compactor v0.1 by default.

The existing V13 field note on the Orchestration Boundary Layer remains the appropriate discovery record for that separate line of work.

## Re-entry Triggers

Reopen active development or evidence work only when one or more of the following occurs:

1. A real user reports a concrete reconnect failure after using the generated routing structure.
2. Multiple independent users identify reconnect trust as a practical adoption barrier rather than a hypothetical concern.
3. An intermediate user demonstrates that the tool helped them migrate an already-grown instruction file into a structure they could not safely produce alone.
4. A repeated real-world failure pattern appears around accumulated local fixes, irrelevant always-active constraints, or route ambiguity.
5. Multi-agent use exposes a concrete limitation that cannot be handled within the existing Compactor boundary.
6. The surrounding agent ecosystem changes enough that conditional routing / skills / scoped instruction loading becomes a common baseline and creates a new, concrete Compactor role.
7. Product pull becomes visible through repeated independent use or other evidence stronger than views, comments, shares, or isolated stars.

When a trigger fires, record the trigger and evidence before changing the gate.

## Do Not Resume Merely Because

Do not reopen active expansion merely because:

- another Reddit angle is available;
- one experienced user is skeptical;
- stars are lower than hoped;
- a new benchmark could make the argument look stronger;
- a new feature idea appears interesting;
- a public post can probably attract a few additional users;
- current attention feels disappointing compared with pre-release expectations.

Those conditions alone do not establish expected value for another active loop.

## Maintenance Policy During Soft Freeze

Allowed maintenance is narrow:

- fix reproducible bugs;
- fix security or privacy defects;
- correct inaccurate documentation;
- repair broken installation or reproduction paths;
- respond to concrete user-reported failures;
- preserve compatibility when a dependency or platform change breaks the shipped path.

Do not add speculative features, marketing-driven surface area, or benchmark scope under the label of maintenance.
